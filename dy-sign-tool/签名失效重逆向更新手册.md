# 抖音 a_bogus 签名失效后 · 重新逆向更新手册

> 目标读者：维护者（你/我）。
> 核心认知：a_bogus 是「常量 + 算法」的混合体。算法（SM3/RC4/置换）基本不变，
> 变的绝大多数是**常量**：盐值 SALT、字母表 ALPHABET、版本号、时间锚点、掩码。
> 所以重新逆向 = **提取新常量 + 对齐算法**，不是推倒重写。

---

## 0. 先判断：签名真的失效了吗？

不要凭感觉。用工具自动探测：

```bash
python update_sign.py --probe --aweme-id <真实视频ID> --cookie "<cookie>"
```

输出：
- `PASS`：签名仍有效，无需更新
- `FAIL 403`：签名被拒，需要更新
- `FAIL 风控`：可能是 IP/频率问题，先换代理重试

> ⚠️ 403 ≠ 一定签名失效，也可能是 cookie 过期/参数错误/IP 风控。
> 至少用**两个不同视频 + 换一次 IP** 复测，确认不是误报。

## 1. 获取最新的 webmssdk.js

抖音的签名代码在 `webmssdk.js` 里。获取方式（三选一）：

### 方式 A：浏览器开发者工具（推荐，最简单）
1. 打开 https://www.douyin.com/ ，F12 → Network
2. 刷新页面，筛选 `webmssdk` 或 `webmssdk.js`
3. 右键 → Save response，保存为 `webmssdk_new.js`

### 方式 B：从页面 JS 里找
在 Console 执行：
```js
performance.getEntriesByType('resource')
  .map(e => e.name)
  .filter(n => n.includes('webmssdk'))
```
拿到 URL 后 `curl -o webmssdk_new.js <URL>`

### 方式 C：直接从现有页面已加载的脚本抓
```js
[...document.querySelectorAll('script')].map(s => s.src).filter(s => s && s.includes('webmssdk'))
```

## 2. 提取关键常量（自动化）

```bash
python update_sign.py --extract --js webmssdk_new.js
```

这会扫描 JS 并尝试提取：
- `SALT`（盐值，字符串）
- `ALPHABET_S3/S4`（两个自定义 Base64 字母表）
- `BDMS_VERSION`（版本号字符串）
- `RC4_KEY_BYTE`
- 时间锚点（FORTNIGHT_EPOCH / DUMP_CLOSURE_TIME）

**注意**：webmssdk.js 是重度混淆的（`_0x` 变量、字符串数组 + 解密函数），
自动化提取只能拿到**部分**常量，特别是：
- 字符串在 JS 里通常被拆成 `_0xabc('0x1')` 这样的解密调用，**直接搜不到明文**
- 字母表/盐值可能藏在数组里，需要配合解密函数还原

所以自动化提取是**辅助**，最终要人工核对（见第 3 节）。

## 3. 手动比对流程（自动化不够时）

### 3.1 准备工具
- 新版 `webmssdk_new.js`（上面拿到的）
- 旧的 `ab_pure.py`（当前可用的，作为基准）
- 一个「已知答案」：在真实浏览器里，对**同一 URL + 同一参数**生成一个真实的 a_bogus（Console 里 `fetch` 或从 Network 里抄一个）

### 3.2 三步定位差异

**Step 1 — 比对输出长度**
新签名的长度变了（比如 192 → 200），说明字符表/载荷结构变了，直接比对常量。

**Step 2 — 找盐值（SALT）**
在 `webmssdk_new.js` 里搜：
```
grep -n "dhzx" webmssdk_new.js          # 旧盐值，看还在不在
grep -n "SALT\|salt\|_0x" webmssdk_new.js | head
```
旧盐值 `dhzx` 若还在 → 盐没变。若搜不到 → 在字符串解密数组里找 4 字符的 `\x64\x68\x7a\x78`（即 "dhzx" 的 hex）。

**Step 3 — 比对字母表**
旧字母表：
```
S3: ckdp1h4ZKsUB80/Mfvw36XIgR25+WQAlEi7NLboqYTOPuzmFjJnryx9HVGDaStCe
S4: Dkdpgh2ZmsQB80/MfvV36XI1R45-WUAlEixNLwoqYTOPuzKFjJnry79HbGcaStCe
```
在新 JS 里搜 `ckdp1h4Z` / `Dkdpgh2Z`（字母表前 8 字符）。
- 搜到 → 字母表没变
- 搜不到 → 字母表变了，需要从混淆数组里还原（配合解密函数，或用 `_0x` 数组还原脚本）

### 3.4 版本号
```
grep -o "[0-9.]*[0-9]-[a-z0-9.]*" webmssdk_new.js | head
```
找类似 `1.0.1.19-fix.01` 的字符串，更新 `BDMS_VERSION`。

## 4. 算法层面的更新（较少见）

如果常量都对上了还是 403，可能是**算法结构**变了（载荷字段增删、置换表变了）。
这种情况自动化帮不上忙，需要：

1. 用断点调试 `webmssdk_new.js`（Chrome DevTools 断点，或 Node + jsdom 补环境直调）
2. 比较新旧函数的**输入输出映射**：同一输入，新旧 a_bogus 的长度/首字符
3. 从「载荷布局」反推字段（对照 `ab_pure.py` 里 L[12]/L[14]/L[23]... 的结构）

> 这一步本质是「补环境直调」路线，比纯重写快得多：
> 把新版 webmssdk.js 直接跑在 Node 补环境里，用真实浏览器返回的签名校准。

## 5. 更新后的验证流程（必须做）

```bash
# 1. 单元自测：签名能生成
python -c "from dy_sign.ab_pure import ABogusPureSigner; s=ABogusPureSigner(); print(len(s.sign('https://www.douyin.com/?a=1')))"

# 2. 线上探测：真实 cookie + 真实视频
python update_sign.py --probe --aweme-id <真实视频ID> --cookie "<cookie>"

# 3. 全流程 POC：BitBrowser 取 cookie → 签名 → 评论接口
python poc_dy_sign.py --window <抖音窗口ID> --sign http://127.0.0.1:8765
```

**验收标准**：`--probe` 返回 PASS + POC 拿到真实评论。

## 6. 更新频率与预案

| 场景 | 行动 |
|---|---|
| 签名失效（403 全量） | 跑 `--probe` 确认 → 按本手册 1~5 更新 |
| 部分接口失效（搜索 403，评论 200） | 可能只有部分接口换算法，只更新对应分支 |
| 长度变了（192→200） | 大概率字母表/载荷变了，重点比对第 3 节 |
| 完全对不上 | 走第 4 节「补环境直调」路线，用真实浏览器生成签名校准 |

---

## 7. 一劳永逸的替代路线（强烈建议评估）

如果「每几个月逆向一次」的维护成本不可接受，推荐升级为**「混合模式」**：
- **主通道**：继续用真实 BitBrowser（签名浏览器自动生成，永不失效）
- **加速通道**：API + a_bogus（本工具），**失效自动回落浏览器**

这样即使签名过期，也只是「加速没了」，采集不会中断。
（这正是 `docs/抖音签名服务集成设计.md` 里的架构——浏览器保底，API 加速。）
