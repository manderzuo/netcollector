# 抖音签名服务集成设计 — a_bogus 纯 API 通道

> ⚠️ **本文档已废弃（2025-08）**：签名模块已按 clean-room 标准重写，
> 新实现位于 `leadharvest`（应用层）与 `dy-sign-tool/signature_rewrite/sig/`（签名算法）。
> 本文档仅作历史记录保留，不再作为实现参考。详见 `docs/cleanroom-重构设计方案.md`。

> 版本：v0.1（评审稿，已废弃）
> 日期：2025-08
> 背景：在「多平台采集工作台」现有 BitBrowser CDP 管线之外，新增一条**纯 API 采集通道**（直连接口 + 自算签名），用于提速/并发；同时保留浏览器管线的稳定兜底。
> 目标原则：**浏览器管线保底，API 通道加速；签名失效自动回落，不阻塞主流程。**

## 0. 结论先行

1. **签名核心代码已存在**：`D:\DSH\DouYin_Spider\utils\` 下有完整的纯 Python a_bogus 实现（`ab_pure.py` + `sm3.py` + `mstoken.py` + `fingerprint.py`），已本地冒烟测试通过（可生成 192 字符 a_bogus）。
2. **接入成本低**：DouYin_Spider 的签名函数是独立纯函数（`generate_a_bogus_pure(api_path, query)`），可抽出为独立签名服务，不依赖其采集框架。
3. **核心风险未消除**：签名**当前有效与否未经线上验证**。抖音升级算法后纯 Python 实现会失效（历史评审已明确此风险）。因此必须内置「签名健康检查 + 自动回落浏览器」机制。
4. **本设计的原则**：签名服务是**可选加速通道**，不是主通道。失效时无缝回落到现有 BitBrowser 管线，用户无感。

## 1. 目标与非目标

### 1.1 目标

| # | 目标 | 说明 |
|---|---|---|
| G1 | 纯 API 采集通道 | 直连 `/aweme/v1/web/comment/list/` 等接口，带上自算 a_bogus，无需开浏览器 |
| G2 | 提速/并发 | API 通道可并发拉评论/搜索，不受浏览器窗口数限制 |
| G3 | 稳定兜底 | 签名失效/风控时自动回落 BitBrowser 管线，不中断任务 |
| G4 | 可观测 | 签名健康状态、API 请求成功率、回落事件全部可视化 |

| # | 不做 | 原因 |
|---|---|---|
| N1 | 不重写签名算法 | 已有 `ab_pure.py` 现成实现，重写无收益 |

| N3 | 不替代浏览器管线 | API 通道是加速选项，浏览器管线仍是稳定底座 |
| N4 | 不做写操作 | 不发布评论/点赞/私信，仅采集公开数据 |

### 3.2 签名服务（独立进程/线程）

**定位**：一个轻量 HTTP 服务，暴露三个接口：

| 接口 | 方法 | 说明 |
|---|---|---|
| `GET /sign?url=...` | 生成 a_bogus | 输入完整 URL，返回 `{"a_bogus": "..."}` |
| `GET /mstoken?ttwid=...` | 获取 msToken | 带缓存（TTL 600s），失败返回空串 |
| `GET /health` | 健康检查 | 返回签名算法版本、上次成功时间、是否已失效 |

**实现要点**：
- 复用 `D:\DSH\DouYin_Spider\utils\` 的 `ab_pure.py` + `mstoken.py`（仅拷贝签名相关文件，不引入整个框架）
- 服务无状态（签名每次实时算，msToken 带进程内缓存）
- 端口建议 `127.0.0.1:8765`（仅本机，无鉴权）
- 用标准库 `http.server` 或 `fastapi` 均可（项目已有 aiohttp）

### 3.3 采集器侧集成（live_collector / dy_collect）

**接入策略：先浏览器，后 API，自动回落**：

```
fetch_comments(vid, url):
    1. 尝试 API 通道（直连 + a_bogus）
    2. 若失败（403/签名失效/风控）→ 记录回落事件 → 走 BitBrowser CDP 管线
    3. 返回结果（API 通道失败次数计入健康状态）
```

**关键决策点**：
- 每次任务开始先打 `/health`，签名失效则全程走浏览器，不浪费请求
- API 通道连续失败 N 次（建议 3）→ 自动熔断，本任务剩余全部走浏览器
- 熔断状态记录到日志/GUI，用户可见

### 3.4 接口参数对齐

参考 DouYin_Spider 已验证的接口结构（旧融合文档也确认过）：

**评论列表**：
```
GET /aweme/v1/web/comment/list/
  aweme_id=<vid>
  cursor=<翻页游标>
  count=<数量, 建议20>
  item_type=0
  device_platform=webapp
  aid=6383
  a_bogus=<签名>
  # 可选: msToken, cookie
响应: { comments: [...], cursor: 下一页, has_more: bool }
```

**二级评论**：
```
GET /aweme/v1/web/comment/list/reply/
  item_id=<aweme_id>
  comment_id=<一级评论id>
  cursor / count / a_bogus
```

**搜索**：
```
GET /aweme/v1/web/general/search/stream/
  keyword=<关键词>
  offset / count / sort_type
  a_bogus
```

> ⚠️ 具体参数以线上抓包为准，签名失效/参数错误都会 403。设计上先做「评论接口」最小验证，跑通后再扩展搜索。

## 4. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| **签名算法失效**（抖音升级） | 🔴 高 | 健康检查 + 熔断 + 自动回落浏览器；失败率 > 阈值时 GUI 醒目告警 |
| **IP/账号风控**（纯 API 高频） | 🟠 中 | 复用现有冷却策略；API 通道限速（默认 2 req/s）；代理可选接入 |
| **参数/结构变化**（接口升级） | 🟠 中 | 先做最小验证再扩展；解析失败计为 API 失败并回落 |
| **msToken 失效** | 🟡 低 | 带 TTL 缓存 + 每次刷新；失败不影响 a_bogus 主签名 |
| **合规风险** | 🟠 中 | 仅采集公开数据自用；遵循既有「非商业化」边界 |

## 7. 开放问题（需评审确认）

1. **cookie 来源**：API 通道需要真实登录 cookie。从 BitBrowser 窗口实时取（`cookies_get`），还是独立维护？→ 建议实时取，避免过期。
2. **并发上限**：API 通道建议并发上限 3~5，超过走浏览器排队。是否可接受？
3. **代理**：API 通道是否需要绑定代理 IP（复用现有代理池）？还是本机 IP 够用？
4. **搜索是否进 API 通道**：评论接口验证通过后，搜索是否也走 API？（搜索风控更严，antispam_check 只认新算法签名，DouYin_Spider 已专门处理）
