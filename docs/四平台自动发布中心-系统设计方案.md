# 四平台自动发布中心系统设计方案

## 1. 建设目标

在现有“多平台采集工作台 2.0”中新增独立的“发布中心”，支持抖音、小红书、B站、微博四个平台，并继续复用现有：

- BitBrowser 窗口与账号绑定；
- 浏览器级 CDP 连接；
- QML 2.0 GUI 与本地后台服务；
- SQLite、任务状态机、人工验证、后台日志和自动恢复；
- 已验证的四平台页面导航、登录诊断和浏览器操作能力。

首要原则是“草稿优先、预览优先、真实发布默认关闭”。发布系统不能破坏采集、线索中心和互动回复功能，也不能在同一个账号上同时执行采集、回复和发布。

## 2. 能力范围

| 平台 | 第一阶段 | 第二阶段 | 推荐执行方式 |
|---|---|---|---|
| 抖音 | 图文、视频填入与预览 | 定时和真实发布 | BitBrowser + CDP；参考现有本地发布技能与 social-auto-upload |
| 小红书 | 图文、视频填入与预览 | 定时和真实发布 | BitBrowser + CDP；参考 XiaohongshuSkills、xiaohongshu-mcp |
| B站 | 视频投稿、动态填入与预览 | 专栏、定时和真实发布 | 浏览器 CDP 为默认；biliup 作为可选视频上传引擎 |
| 微博 | 文字、图片填入与预览 | 视频、定时和真实发布 | BitBrowser + CDP；参考 Playwright 发布脚本的定位策略后自行实现 |

不在首版范围内：自动规避验证码、批量养号、自动切换身份、无确认高频发布、绕过平台风控。

## 3. 总体架构

```text
发布中心 QML 界面
  ├─ 内容编辑、素材、平台版本、预览、审核
  ├─ 发布队列、状态、失败重试、发布记录
  └─ 真实发布总开关（每次启动默认关闭）
                  │ 本地命令/增量事件
                  ▼
PublishingService（后台发布服务）
  ├─ DraftService       草稿和平台版本
  ├─ AssetService       图片/视频检查与转码
  ├─ PublishScheduler   定时、队列、账号互斥、恢复
  ├─ PublishPolicy      审核、频率、真实发送资格
  ├─ ResultVerifier     发布结果确认与防重复
  └─ AdapterRegistry    四平台发布适配器
          │
          ├─ DouyinPublisher ─────┐
          ├─ XiaohongshuPublisher ├─ BitBrowser + CdpSession
          ├─ WeiboPublisher ──────┤
          └─ BilibiliPublisher ───┘
                       └─ 可选 BiliupVideoEngine
                  │
                  ▼
SQLite + operation_events.jsonl + 截图/页面证据
```

外部开源项目只作为算法、选择器和流程参考，不直接接管账号、Cookie、数据库、GUI或浏览器生命周期。

## 4. 统一发布适配器

四个平台均实现同一份协议：

```python
class PublisherAdapter(Protocol):
    platform: str

    def capabilities(self) -> PublishCapabilities: ...
    def validate(self, variant, assets, account) -> ValidationResult: ...
    def prepare(self, context) -> PrepareResult: ...
    def open_editor(self, context) -> ActionResult: ...
    def fill(self, context) -> ActionResult: ...
    def inspect_preview(self, context) -> PreviewSnapshot: ...
    def submit(self, context) -> ActionResult: ...
    def verify(self, context) -> PublishResult: ...
    def recover(self, context) -> RecoveryResult: ...
```

统一原则：

1. `fill()` 只能填写内容，绝不能隐式点击发布。
2. `submit()` 必须收到后台生成的单次授权令牌才允许执行。
3. 页面元素优先使用语义、DOM层级和实时盒模型定位，不保存固定坐标。
4. 坐标点击只能作为第二道防御，并且每次点击前重新解析元素位置。
5. `verify()` 必须独立于 `submit()`，不能因为点击成功就标记发布成功。
6. 所有适配器输出相同错误分类，GUI不解析平台私有异常字符串。

## 5. 平台实施方法

### 5.1 小红书

主要参考 `white0dew/XiaohongshuSkills` 的 Windows、远程 CDP、图文/视频和预览模式；参考 `xpzouying/xiaohongshu-mcp` 的登录检查、发布结果和错误处理。

实施流程：

1. 打开选定的小红书 BitBrowser 窗口；
2. 每次任务重新导航到创作中心初始发布页，不复用上次遗留编辑页；
3. 检测登录、发布类型和编辑器是否加载；
4. 上传图片或视频，等待平台完成处理；
5. 填入标题、正文、话题；
6. 读取页面中的实际内容形成预览快照；
7. 默认停在发布按钮之前；
8. 真实发布时点击按钮，并从成功提示、作品链接或创作记录中确认结果。

### 5.2 抖音

复用现有抖音页面诊断、Note类型识别、BitBrowser连接和CDP工具；参考 `social-auto-upload` 的图文/视频发布步骤与定时任务接口。

必须分别维护图文和视频两个流程，不能用一个编辑器选择器兼容所有内容。上传后应等待平台转码、封面和话题控件稳定，再允许预览或提交。

### 5.3 B站

采用双引擎：

- 默认浏览器引擎：复用选定 BitBrowser 账号，适用于动态、专栏、视频投稿预览，账号体系最一致；
- 可选 `biliup` 引擎：只用于视频上传，适合大文件、多P和上传线路处理。

首版先完成浏览器模式。`biliup` 必须封装成独立子进程，通过结构化 JSON 输入输出，不允许直接访问主数据库。账号凭证按账号隔离，日志中禁止记录 Cookie、SESSDATA、CSRF 或访问令牌。

B站内容类型分开建模：`video`、`dynamic_text`、`dynamic_image`、`article`，不同类型拥有独立校验规则和编辑器流程。

### 5.4 微博

微博缺少经过大量用户验证的高星发布引擎，因此只参考开源 Playwright 脚本的多选择器、图片上传和错误截图思路，核心代码由项目自行实现。

首版支持文字和图片微博。按钮定位使用：可见文本、可访问属性、组件状态、编辑器邻接关系和实时盒模型的组合验证；不能仅凭“发布”两个字点击页面中的任意按钮。提交后通过发送成功提示、内容消失与首页最新微博三项组合确认。

## 6. 发布业务流程与状态机

```text
草稿
  → 待完善
  → 待审核
  → 已批准
  → 待发布
  → 正在打开账号
  → 正在上传素材
  → 正在填写
  → 预览就绪
  → 等待人工确认（真实发布关闭时停在这里）
  → 正在提交
  → 正在确认结果
  → 已发布

任意执行状态可进入：
  需要人工验证 / 已暂停 / 可重试失败 / 永久失败 / 已取消 / 结果不确定
```

“结果不确定”不能自动重试。后台必须先检查账号近期内容，排除已经发布成功后才能重新提交，避免重复发布。

人工验证恢复后继续原账号、原平台、原任务和原步骤，禁止自动切换账号。

## 7. 数据模型

新增表，不修改现有采集、评论、线索和互动核心表：

### `publish_drafts`

保存内容主题、原始正文、创建人、审核状态、版本号和更新时间。

### `publish_variants`

一条草稿对应四个平台版本，保存平台、内容类型、标题、正文、话题、封面、平台设置及人工修改结果。

### `publish_assets`

保存源文件、派生文件、类型、尺寸、时长、哈希、校验结果。原始文件不覆盖，平台裁剪或转码结果单独保存。

### `publish_jobs`

保存平台版本、账号、计划时间、当前状态、当前步骤、真实发布授权、重试次数、最终作品ID和URL。

### `publish_attempts`

每次执行保存 `run_id`、开始/结束时间、页面URL、操作步骤、结果、错误分类、截图和证据路径。

### `publish_account_locks`

保证一个账号同一时刻只能执行采集、回复或发布中的一种浏览器任务。

所有表通过新增迁移创建，安装前自动备份数据库，迁移失败自动回滚。

## 8. 发布中心界面

左侧新增“发布中心”TAB，内部采用一页多状态池：

### 顶部

- 新建内容；
- 批量导入；
- 平台筛选、账号筛选、状态筛选、时间筛选；
- 真实发布开关；
- 暂停全部发布。

### 左侧列表

- 草稿箱；
- 待审核；
- 待发布；
- 发布中；
- 已发布；
- 失败/人工处理。

### 中部编辑区

- 原始内容；
- 抖音、小红书、B站、微博四个平台版本Tab；
- 标题、正文、话题、内容类型和平台专属设置；
- 素材拖入、排序、封面选择和错误提示。

### 右侧预览与执行区

- 平台预览；
- 当前账号；
- 计划时间；
- 校验结果；
- “填入浏览器预览”；
- “批准并进入待发布”；
- “确认真实发布”。

真实发布确认弹窗必须显示平台、账号、标题、素材数量和任务数量，位置由当前主窗口计算，不能出现在桌面左上角。

## 9. 账号、队列和安全控制

- 发布账号直接复用现有 `accounts` 与 `bb_window_id`；
- 账号下拉只显示同平台账号；
- 每个账号独立串行队列，不同账号可以并行；
- 账号执行发布时，采集与互动任务等待账号锁；
- 打开窗口后先检查当前域名、登录状态和可操作页面；
- 检测到登录、验证码、灰屏、滚动失效或编辑器不可用时进入人工处理；
- 真实发布总开关每次程序启动默认关闭；
- 批量真实发布需要二次确认，单项失败不能影响已经成功的平台；
- 账号频率、每日数量和工作时段可配置，但不提供绕过平台安全机制的功能。

## 10. 日志、诊断与结果证明

每个发布任务生成唯一 `run_id` 和 `job_id`，完整记录：

- 调用入口、操作者和内容版本；
- 选择的平台、账号和窗口ID；
- 浏览器打开结果、页面URL、目标Tab；
- 每次DOM查询策略、候选数量和最终命中理由；
- 点击元素的标签、文本、属性、实时坐标和盒模型；
- 上传文件名、大小、哈希和平台处理状态；
- 填写前后内容摘要；
- 提交前截图、提交后截图和成功证据；
- 人工验证、超时、页面跳转和重试决策。

日志自动脱敏，不记录API Key、Cookie、Token及完整私密内容。继续沿用每小时快照、实时查看和一键导出功能。

## 11. 测试与验收

### 自动测试

1. 数据迁移与回滚测试；
2. 四平台适配器契约测试；
3. 字数、素材、标签和内容类型校验测试；
4. DOM固定样本与选择器回归测试；
5. 模拟CDP的导航、上传、填写、验证和失败恢复测试；
6. 账号锁、暂停、继续、崩溃恢复和防重复测试；
7. QML按钮、弹窗、筛选和后台协议测试；
8. 原采集、线索和互动中心全量回归测试。

### 真实浏览器测试

每个平台均按以下顺序验证：

1. 打开正确账号和正确创作页面；
2. 只上传素材，不填写；
3. 填入完整内容，不发送；
4. 调整窗口大小和位置后重复，确认不依赖固定坐标；
5. 关闭后恢复任务；
6. 测试账号发布一条非敏感内容；
7. 确认作品ID、URL、后台记录和页面结果一致。

任何代码修改后执行自动冒烟测试；通过后自动重启GUI并加载后台监控，再由人工进行真实浏览器验证。

## 12. 分阶段实施顺序

### P0：基线冻结与开源审计

- 固化现有采集和互动回归测试；
- 单独下载并审计参考项目；
- 建立许可证和来源记录；
- 不把外部项目直接加入主运行依赖。

### P1：发布中心骨架

- 数据库迁移、后台协议、发布状态机、账号锁；
- QML发布中心；
- 草稿、素材、平台版本和预览数据；
- 暂无真实平台操作。

### P2：小红书和抖音

- 先实现图文，再实现视频；
- 完成“打开—上传—填写—预览”，真实发布保持关闭；
- 真实浏览器稳定后增加提交和结果确认。

### P3：微博和B站浏览器模式

- 微博文字/图片；
- B站动态、视频投稿和专栏；
- 完成四平台统一预览和任务恢复。

### P4：定时、批量和可选 biliup

- 定时队列、批量审批、失败重试；
- 接入可选 B站视频上传子进程；
- 发布记录、统计和内容复用。

### P5：正式验收与发布

- 四平台真实测试账号全流程；
- 原功能全量回归；
- 干净发布包、升级迁移、回滚包和更新说明。

## 13. 最终决策

1. 发布中心是现有工作台的新业务模块，不另起软件。
2. BitBrowser 是四平台账号与登录态的唯一来源。
3. 浏览器CDP是统一默认执行引擎，B站视频可选用 biliup 加速。
4. 外部项目只提供流程、选择器和实现参考，核心适配器由本项目维护。
5. 默认只填入和预览，真实发布必须显式开启并二次确认。
6. 发布成功必须有可验证证据，点击按钮本身不等于成功。
7. 首先实现小红书与抖音，再完成微博和B站，最后开放定时和批量真实发布。
